### JPQL

- JPA를 사용하면 엔티티 객체를 중심으로 개발하게 되는데

- 검색쿼리를 객체 중심 쿼리로 짜기어려움

- 엔티티 객체를 대상으로 검색하려고 할 때 모든 DB데이터를 객체로 변환해서 검색하는 건 불가능하다.

- 필요한 데이터만 DB에서가져오기 위해선 SQL이 필요하다.

- SQL을 추상화한 객체 지향 쿼리 언어

- JPQL 은 엔티티 객체를 대상으로 쿼리 : 결국 SQL로 변환되서 실행됨

```java
List<Member> result = em.createQuery(
    "select m from Member m where m.username like "%kim%""
).getResultList();
```

- 여기서 사용되는 Member은 엔티티이다. 테이블이 아닌

- 실행 시키면 JPA가 적절한 매핑 정보를 읽고 Member 엔티티에 대해 SQL문을 만들어 낸다.

- select 뒤에 \*이 아닌 m 이 들어온다 m은 member 객체를 의미한다.

### JPQL은 객체 지향 SQL

## Criteria

- JPQL은 문자이다. 단순한 String 을 문자열로 둘 수 밖에 없음

- 그럼 동적인 쿼리를 만들기 어렵다.

- username을 입력 받고, null 이 아닐 때 JPQL 명령 문자열에 추가하고 ... 이런거 하나 하나 띄어쓰기 까지 신경쓰면서 작성하는게 매우 번거롭다.

- 문자열을 건드리는게 버그나기 좋다.

- MyBatis 의 장점이 동적 쿼리를 쓰기 좋음

```java

// Criteria 사용 준비 : java 표준
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Member> query = cb.createQuery(Member.class);

Root<Member>m = query.from(Member.class);


CriteriaQurey<Member> cq = query.select(m).where(cb.equal(m.get("username")));

//  java 코드 형태로 코드를 짜고 있다.
// 오타도 컴파일 오류로 버그를 찾을 수 있다.
// 동적 쿼리를 짜기 훨씬 좋다.

// 단점 : SQL 스럽지가 않다. 안쓴다. 보기 힘들어

```

- 안쓴다.

- 문자가 아닌 java 코드로 JPQL을 작성할 수 있고, 빌더 역할
- 너무 복잡, 실용성 없음
- 대신 QueryDSL 사용

## QueryDSL : 오픈소스 라이브러리

```java
QMember m = QMember.member;
queryFactory
    .select(m)
    .from(m)
    .where(m.name.like("kim"))
    .orderBy(m.id.desc())
    .fetch();
```

- 동적 쿼리도 쉽게 생성할 수 있음

- 단순하고 쉽다. 실무 사용 권장
