## 상속관계 매핑

- 관계형 DB는 상속이라는게 없음

- 대신 슈퍼타입, 서브타입 관계 모델링 기법이 객체 상속과 유사하다.

- 상속관계 매핑 : 객체의 상속과 구조 - DB의 슈퍼타입, 서브타입 관계를 매핑

### 슈퍼타입, 서브타입 논리 모델을 물리 모델로 구현하는 3가지 방법

1. Join 전략

- Item 테이블을 만들고, 앨범, 영화, 책 테이블을 Join으로 가져오기.

  - DTYPE 같이 구분하는 필드 사용

2. 단일 테이블 전략

- 논리 테이블 하나만 잡아서다 합쳐 버림

  - DTYPE 으로 타입만 구분

3. item 하위가 아니라 각각 구현하기

### 하지만 객체 입장에서는 3가지 물리 모델이 아닌 상속 관계로 보인다.

- DB에서 어떤 방식으로 논리 모델을 구현했던, JPA가 매핑을 지원한다.

## Extends Item 으로 단순 실행 하면 ..

    - 기본 전략 : Item 이라는 하나의 테이블에 다 들어옴

1. 조인 전략

- Name, Price 중복이 안됨, 가장 정규화 된 형태

```java
@Entity
@Inheritance(strategy = InheritanceType.JOINED)
```

설정 시, 각각의 ALBUM, BOOK, MOVIE 테이블이 create

- movie의 새로운 객체를 만들때, em.persist() 를 실행하면 ..

  - Insert into Item, Insert into Movie 이렇게 2개의 INSERT 문이 나가는 것을 확인할 수 있음

- em.find(Movie.class, movie.getId()) 로 새롭게 DB에서 조회하면...

  - Inner Join을 통해 Item테이블과 Movie테이블 을 조인하여 결과를 찾아준다.

```java
@DiscriminatorColumn()
부모 타입

@DiscriminatorValue()
자식 타입
```

- DTYPE이라는 필드가 생긴다.

- DB입장에서 어떤 타입의 테이블(객체)에서 요청이 들어왔는지 모를 수 있다.

- DTYPE을 통해 어떤 타입인지 바로바로 알 수 있다.

2. 싱글 테이블

- 단일 테이블전략

```java
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
```

- ITEM 테이블에 모든 자식들의 속성이 다 들어가 있다.

- insert, select 도 쉬움

- 성능상 이점 존재

- @DiscriminatorColumn 이 없어도 그 필드가 생성됨(이게 없으면 어떤 타입인지 알 수 없기 때문에)

## 성능을 보고 상속 관계 매핑 전략을 쉽게 바꿀 수 있음

```java
@Inheritance(strategy = InheritanceType.JOINED)
```

이것만 바꾸니까 다른 코드를 바꿀 필요가 거의 없더라

3. 구현 클래스 따로 따로 전략

- Item 테이블을 따로 두지 않고, 구현 클래스들을 둔다.

- Item class를 추상 클래스로 만들면 Item 테이블은 CREATE 되지 않는다.

- 대신 Movie 같은 구현 클래스 안에도 다른 테이블 공통 필드를 다 가지고 있어야 한다.

- Discriminator 필드가 필요가 없음(다 따로 있으니까)

### 단점

- 조회를 할 때 Item 타입으로 조회하면?

- union all 으로 다 뒤진다.

- item_id 만 아는 상황에서 album, movie, book 중 뭔지 모르는 상황임

- 조회를 위하여 3개의 테이블을 다 찾아야 한다.

## 각 전략의 장단점

### 1. 조인 전략

### 장점

- 테이블이 정규화
- 외래 키 참조 무결성 제약조건(ITEM_ID 쓸 수 있음.)
- 저장공간이 효율화

### 단점

- 조회할 때 조인 많이
- 조회 쿼리 복잡
- 데이터 저장시 insert sql 2번

### 2. 단일 테이블 전략

### 장점

- 조회 성능
- 조회 쿼리 단순

### 단점

- 자식 엔티티 매핑 컬럼은 모두 null 허용
- 모든걸 단일테이블 : 테이블이 커져서 조회 성능이오히려늦어짐

### 3. 구현 클래스마다 테이블전략 (쓰면 안되는 )

- 묶이는 무언가가 없음

### 장점

- 서브 타입을 명확하게
- not null 제약 조건 사용 가능

### 단점

- 여러 테이블 함께 조회할 때 매우안좋음 union
- 자식 테이블 관리 어려움
- 새로운 타입이 새롭게 추가될 때 코드 수정 많이

## 정리

- 관계형DB는 상속관계가 없음
- 슈퍼타입, 서브타입 관계
- 3가지 전략 : 조인 + 단일 테이블 + 구현 클래스별 테이블

- JPA는 어노테이션을 통해 전략 선택 가능하다.

### tradeoff

- 조인 vs 단일테이블

- 조회 성능 vs 정규화 vs 미래 수정 가능성 vs 단순함
